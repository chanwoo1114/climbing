# Climbing — 개발 정의서 v3

> 클라이밍 암장 정보 + 기록(로그) SNS + 커뮤니티 + 크루 + AI 자세 분석 서비스. 포트폴리오/학습 목적.
> 모노레포 구조: `climbing/backend`(Django + DRF), `climbing/front`(React SPA)
> v2 → v3 변경: 크루(풀 버전 — 크루 피드, 크루 주최 모집, 크루 단톡방, 프로필 크루 뱃지) 추가. 디자인 시스템 Chalk & Terra 확정

---

## 1. 프로젝트 개요

클라이머가 **암장을 찾고**, **등반 기록을 남기고**, **피드·커뮤니티로 소통하고**, **AI로 자세를 분석받는** 서비스.

핵심 가치 흐름:
1. 암장 검색 → 방문/등반 → 기록 작성 → 피드 공유 → 좋아요/댓글/팔로우 → DM
2. 모집글 작성 → 참여 신청 → 마감 → 그룹 채팅방 자동 생성 → 함께 투어
3. 크루 생성/가입 → 크루 단톡방 → 크루 피드로 크루원 기록 모아보기 → 크루 주최 투어 모집
4. 등반 영상 업로드 → AI 자세 분석 (비동기) → 관절 오버레이 + 지표 리포트

## 2. 기술 스택

### Backend
| 항목 | 선택 | 비고 |
|---|---|---|
| Framework | Django 5.x + DRF | 기존 코드 유지 |
| 인증 | SimpleJWT (access + refresh) | refresh 토큰 회전 |
| DB | PostgreSQL + **PostGIS** | Gym 위치 PointField, 거리/뷰포트 검색 |
| API 문서 | drf-spectacular | Swagger UI |
| 실시간 채팅 | **Django Channels + Redis** | DM + 모집 그룹 채팅 |
| 비동기 작업 | **Celery + Redis** | AI 영상 분석 파이프라인 (v2에서 필수로 승격) |
| AI 분석 | **MediaPipe Pose + OpenCV** | CPU로 비동기 처리, GPU 불필요 |
| 파일 저장 | S3 (presigned URL) | 영상/이미지 클라이언트 직접 업로드 |
| 컨테이너 | Docker Compose | web + db + redis + celery-worker |

## 4. 신규 모델 설계 (v2 추가분)

### community 앱
```python
Post          # user FK, category(free/recruit), title, content, view_count, BaseModel
PostImage     # post FK, image URL, order
PostComment   # post FK, user FK, content, parent FK(self, null) — 대댓글
Recruitment   # post OneToOne, gym FK, meet_at(DateTime), capacity,
              # join_type(instant/approval), status(open/closed/canceled),
              # chat_room FK(null) — 마감 시 생성된 채팅방 연결
Participation # recruitment FK, user FK, status(pending/approved/rejected/canceled)
              # unique(recruitment, user)
```

모집 마감 플로우 (서비스 레이어, `transaction.atomic`):
1. 정원 도달 or 작성자 수동 마감 → status=closed
2. approved 참여자 + 작성자로 ChatRoom(is_group=True) 생성
3. ChatRoomMember 일괄 생성, Recruitment.chat_room 연결
4. 시스템 메시지 발송 ("OO암장 투어 채팅방이 생성되었습니다")

동시성 주의: 선착순 참여는 `select_for_update()`로 정원 초과 방지.

### crews 앱
```python
Crew        # name, description, image, home_gym FK(null), owner FK,
            # join_type(instant/approval), max_members,
            # chat_room OneToOne — 생성 시 그룹 채팅방 자동 생성
CrewMember  # crew FK, user FK, role(owner/staff/member),
            # status(pending/active), joined_at, unique(crew, user)
```

크루 관련 규칙:
- 유저는 여러 크루 가입 가능하되, 프로필 대표 크루는 1개 (UserProfile.main_crew FK, null)
- Recruitment에 crew FK(null) 추가 — 크루 주최 모집. null이면 개인 모집
- 가입 승인 → CrewMember.status=active + ChatRoomMember 생성 (transaction.atomic)
- 강퇴/탈퇴 → 채팅방에서도 제거, 시스템 메시지 발송
- 크루 피드 = 크루원들의 is_shared=True ClimbLog (권한: 크루원만 조회 or 공개 — 크루 설정)

### analysis 앱
```python
VideoAnalysis # climb_log OneToOne, status, error_message,
              # keypoints JSONB (샘플링된 프레임별 33개 랜드마크),
              # metrics JSONB (무게중심 궤적, 각도 통계, 무브 비율),
              # processed_at, BaseModel
```

파이프라인 (Celery):
```
영상 업로드 완료 → analyze_video.delay(analysis_id)
  → S3에서 영상 다운로드 (임시 파일)
  → OpenCV 프레임 추출 (예: 10fps 샘플링)
  → MediaPipe Pose로 프레임별 33 keypoints
  → 지표 계산 (numpy)
  → JSONB 저장, status=done
```
- CPU 처리 기준 1분 영상 ≈ 수 분 소요 → "분석 중" UX 필수
- 영상 길이 제한 (예: 최대 2분), 해상도 다운스케일 후 처리
- 실패 시 status=failed + error_message, 재시도 1회

## 5. 기존 모델 개선 사항 (v1과 동일)

1. `GymPrice.__str__` / `GymFacility.__str__`의 `self.name` 버그 수정
2. Gym lat/lng Float → PostGIS PointField + GiST 인덱스
3. difficulty 자유 문자열 → GymDifficulty 정규화
4. soft delete 통일: 공용 BaseModel + Manager
5. SocialAccount.access_token 평문 저장 제거
6. ChatRoom 1:1 중복 방지 로직
7. 피드/모집 목록용 인덱스 설계

```
              join(POST), cancel(DELETE),
              participants(GET), close(POST, 작성자만)
  crews/      CRUD ?gym=&q=&cursor=, {id},

              {id}/members/{user_id}(PATCH 승인/역할, DELETE 강퇴),
              {id}/feed(GET), {id}/recruitments(GET)

ws/chat/{room_id}/
```
